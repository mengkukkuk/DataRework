01Executive summary

DataRework is a PySide6 desktop tool for finding and correcting production packaging records in PostgreSQL. Operators search a flattened record set or browse a carton → inner → display → unit tree. Admin actions update records and packaging links together; a separate Windows service later recomputes serial usage totals.

The database package already separates query, hierarchy, rename and synchronization concerns. The next useful step is to make that foundation safer, then add explicit query fields and predictable paging. Fix password verification before expanding access.

500 rowsCurrent record query limit; no database ordering
One commitGrid records, edge updates and activation changes
10 secondsSync sleep after each cycle, not a freshness guarantee

To query more data: adding records, adding columns, joining reference data and returning more than 500 results are different changes. Section 6 explains each path. A new column can appear automatically in the grid, but a new filter still needs UI wiring.

Evidence: main_window.py, db/queries.py, db/edge_mirror.py, serial_store_aio.py.

02System architecture

Implemented

There is no HTTP application server in this repository. Both executables connect directly to PostgreSQL through db.get_connection(). The GUI and the sync service are separate processes.

03How functions work together

Choose an operation to follow its call path. The steps describe current code, including transaction boundaries.

Search records and browse containers

  1. Start the app and resolve access

    main() loads Qt → App opens LoginWindow → _attempt_login() calls db.authenticate() → MainWindow(username, permission, tag_name). The operator tag is required when constructing the window, including in tests. A rejected authentication result is handled before unpacking the permission/tag pair. DEV_MODE skips login and grants the UI admin status.

  2. Discover columns and build filter choices

    _refresh_dependent_combos() calls get_columns() and fetch_distinct_values(). Cascade order is assignment → product, scoped by month/year. _refresh_tag_values() loads identifiers for the selected category and tag.

  3. Search using parameterized conditions

    _on_search() combines _current_conditions() and _category_tag_condition(), looks up primary keys, then calls query_rows(). It returns (column_names, rows).

  4. Populate the record grid

    _populate_table() stores original values and primary keys for later comparison. Admins can edit if a primary key exists; container serial and roll columns remain read-only.

  5. Browse the same data as packaging

    _refresh_containers() → container_groups() → ContainerPanel.set_groups() → build_hierarchy(). Opening records passes the entire selected ancestor path to _on_search(container_path=...), preserving context for repeated serial names.

Edit and delete records

  1. Stage changes locally

    _on_item_changed() highlights edits; _delete_selected_rows() marks delete checkboxes. Neither writes to PostgreSQL.

  2. Collect the intended operation

    _on_save() checks admin permission and primary keys, then _collect_changes() returns update pairs and delete key tuples. Empty strings become None. The operator confirms the change.

  3. Read originals and validate shared edges

    save_grid_changes() opens one connection. _update_staging_serial_data() reads pre-edit rows and rejects serial/roll edits whose child edge is shared, raising SharedEdgeError.

  4. Update packaging and serial state

    _apply_edge_change() updates affected edge endpoints. Unit serial changes deactivate the old serial and activate the new one. Grid saves pass tag_name=self.tag_name by keyword so the database schema remains public; activation updates write that tag to staging_serial_data.activated_by. Deleting a unit deactivates its serial and removes its unit edge; shared parent edges stay.

  5. Write the grid changes and commit once

    queries._save_changes() updates/deletes the flattened records on the same cursor. Errors roll back both phases; unique violations become SerialConflictError. On success, _on_search() reloads the grid. Roll usage totals update later.

Rename an entire packaging object

  1. Start with a dedicated dialog

    _rename_container() accepts a grid context action, footer action or container-card signal. It rejects pending grid edits and requires admin access.

  2. Preview the full impact

    container_rename_preview() counts matching flattened rows and edges. The user confirms the rename. This scope is serial + level, not the current grid filters or visible 500 rows.

  3. Rename every matching reference

    rename_container() checks the replacement serial with _serial_in_use(), then _apply_serial_rename() changes child and parent edge mentions plus the flattened level column. Unit renames also update activation flags. This operation commits once.

  4. Optionally relabel children in a separate transaction

    After the parent commit, _relabel_children() loads container_children(). ChildRelabelDialog proposes child names; rename_children() validates and commits the selected batch atomically. Declining or failing this second stage leaves the parent rename in place.

  5. Refresh the view

    _on_search() reloads records; a rename from the manager also refreshes container groups.

Recompute serial usage in the background

  1. Ensure the Windows service is running

    main() schedules ensure_service_running() using QTimer.singleShot(0, ...). NSSM supervises the source script or packaged SerialStoreSync.exe. Installation may request Windows elevation.

  2. Fetch active counts

    run_forever() calls sync_used_serials_once(). asyncio.to_thread() runs _fetch_active_counts(), grouping serial rows by non-null roll number and counting activate = true.

  3. Apply counts using another connection

    _apply_used_serials() writes serial_store.used_serials. Unmatched non-null store roll numbers reset to zero; an empty count map resets every store row. A null store roll number is not matched by NOT IN in a nonempty cycle.

  4. Log and repeat

    A failed cycle is logged and the loop continues after the configured sleep, default 10 seconds. Read and write use separate connections, so counts can already be stale when written. The next successful cycle reconciles them.

Function sources: main_window.py, edge_mirror.py, containers.py, serial_store_aio.py.

               ["JOB-DEMO"])]

save_grid_changes(table, pk_columns,
                  updates=[((row_id,), {"unit_serial_no": "U-NEW"})],
                  deletes=[], tag_name="OPERATOR-TAG")

Identity limitation: generic writes accept multiple primary-key columns, but edge mirroring reads only pk_columns[0] and the first tuple value. Do not treat composite-key support as complete. Grid saves should use the combined API; calling the standalone mirror and write functions separately loses the shared transaction.

06Add more queryable data

Proposed development

Choose the kind of extension first. These are development recipes, not changes already applied to the application or database.

Example implementation path for batch_no

Assume operators need to find all units in a production batch. Define whether the batch belongs to an assignment, a unit or another entity before choosing where to store it. The example below assumes an ordinary column on the editable grid table.

  1. Inspect the deployed schema. Confirm that filling_product_logs is an appropriate writable base table, find its real primary key, and identify the upstream producer. If it is maintained by external transforms or triggers, change that pipeline too.
  2. Add a versioned migration and backfill. Add a nullable text field first. Populate it from an authoritative source and verify unmatched records before deciding on a required constraint. Existing data must remain searchable while the backfill runs.
  3. Let schema discovery expose the field. get_columns() and _populate_table() already load new columns. This does not create a filter and, for admins with a primary key, it may make the new field editable automatically. Explicitly protect derived or controlled fields.
  4. Register the filter and its widget. Update FILTER_COLUMNS, CASCADE_FIELDS, _build_filter_bar() and _cascade_combos. Insert the field at the appropriate cascade position.
  5. Add display labels. Add batch_no and the placeholder text to both locales/en.json and locales/th.json. Preserve raw column names and data values.
  6. Verify both views. Existing shared condition builders should feed record search and container aggregation. Test that batch selection refreshes identifier choices, clears correctly and scopes container counts consistently.

_current_conditions() and _refresh_dependent_combos() iterate these mappings, so a correctly registered combo participates without a separate ad hoc SQL query. Review clear/reset logic and layout whenever adding a widget.

-- Example only. Validate the actual base table before making a migration.
ALTER TABLE public.filling_product_logs
    ADD COLUMN batch_no text;

-- Candidate index after checking representative query plans and selectivity.
CREATE INDEX idx_filling_batch_created
    ON public.filling_product_logs (batch_no, created_at);

The index is a candidate, not a measured recommendation for the live database. Plan locking and rollback for the deployed table size. To back out the UI rollout, keep the added column/data and disable the new filter rather than dropping useful data.

Add production records through a validated import

The current GUI supports search, updates, deletions and renames; it has no create-row or CSV import workflow. Adding arbitrary rows only to the flattened table can leave packaging and usage data inconsistent.

  1. Obtain the actual DDL, foreign keys, unique rules and upstream ingestion contract. Decide which source owns flattened-record generation.
  2. Build a separate import service/function with a dry-run result: accepted rows, rejected rows and reasons. Validate serials, label levels, roll existence, parent references and identifier uniqueness.
  3. Use a source-system record key for idempotency so retrying the same import does not duplicate units. Do not substitute serial text for a verified stable key.
  4. Write the required edge, serial-inventory, roll-inventory and flattened records through the authoritative pipeline in one appropriate transaction. If triggers derive one representation, do not also duplicate their writes.
  5. Reconcile unit counts, packaging paths and activation counts on a test database. Include invalid-parent, duplicate-record, missing-roll and rollback cases.
  6. Search using the imported record dates and assignment/product values; clear default month/year filters if necessary. Verify serial totals after a successful sync cycle.

Suggested new module: db/imports.py for validated persistence, with a separate UI preview. Keep import rules out of _populate_table(). Test fixtures should model real relationships, not just a flat list of rows.

Add related product or supplier data

Use a stable key such as a product ID rather than joining on a display name. A one-to-many join can duplicate unit records and inflate container counts; define whether a relationship is one-to-one, many-to-one or aggregated before exposing it.

  1. Introduce a versioned product/reference schema and a verified join key, with duplicate and orphan checks.
  2. Create an explicit read query or read-only database view projecting the extra fields. Keep the editable base-record ID separate from display fields.
  3. Mark joined/derived columns read-only and route edits to their owning entity. Do not send the projected row blindly to save_grid_changes().
  4. Extend filter metadata with allowed operators and typed values. Reuse the same join/filter semantics in record and container-count queries.
  5. Test missing reference data, duplicate matches and unchanged unit counts. Confirm that no joined column becomes implicitly writable.

Configuration caveat: pointing STAGING_TABLE at a view is not enough for an editable screen. Primary-key discovery may return no key, edge mirroring assumes the existing shape, and the current main-window rename calls still use default table arguments.

Query beyond the current 500-row cap

Increasing the limit alone does not provide predictable browsing. First define a stable ordering, then add paging and pass sorting into SQL.

  1. Choose an ordering backed by verified keys, for example created_at, id if those columns exist and id is unique. Decide how null dates sort.
  2. Add a page result contract with rows, continuation cursor and a has_more indicator. Fetch one extra row to detect the next page.
  3. Use keyset paging for large datasets, with bound cursor values and allowlisted sort identifiers. Ensure the next-page predicate matches the order exactly.
  4. Move search/aggregation to a Qt worker thread; deliver results to the GUI thread and ignore stale responses after filter changes.
  5. Block or resolve pending edits before changing pages. Preserve identities separately from display positions. Export all matches through an explicit export query rather than the currently loaded grid.
-- Proposed shape only; assumes non-null created_at and a unique id.
SELECT id, created_at, assignment_no, product_name
FROM public.filling_product_logs
WHERE assignment_no = %s
  AND (created_at, id) > (%s, %s)
ORDER BY created_at, id
LIMIT %s;
-- First page omits the cursor predicate; request page_size + 1 rows.

Acceptance check: load more than 500 matching test rows with duplicate timestamps. Traverse pages without duplicates or omissions in a fixed dataset, test both sort directions, and define expected behavior under concurrent inserts.

07Key findings and implications

These findings come from the inspected code. Severity expresses development priority; it is not a claim that a production incident has occurred.

Critical — The login function does not verify the submitted password

db/auth.py:authenticate() reads the stored password and checks only that it is nonempty. The bcrypt check is inside a multiline string, and the function then returns the permission/tag pair. A known username with a nonempty stored hash can pass regardless of the submitted password. Restore actual verification, reject invalid hashes safely, and add success/failure tests. Ensure production cannot enable the DEV_MODE admin bypass.

High — New columns and identity fields are editable by default

_populate_table() protects only the listed container serial/roll columns. Other columns, including keys and source/target IDs, may be editable for admins. _collect_changes() sends changed text with no column-type validation. Replace this with an explicit editable-field allowlist and typed validation at both UI and persistence boundaries.

High — Rename scope and table configuration need a single contract

Container renames match serial plus label level across the table, not the selected assignment or ancestor path. Verify whether serials are globally unique. Also, main-window preview/rename/child-relabel calls omit table=STAGING_TABLE, whereas grid search and save use it. With a nondefault configured source, these operations can refer to different flattened tables. Centralize dataset configuration and test a nondefault table.

High — Concurrency and database constraints are not established

Rename conflict checks occur before writes, without a visible locking strategy. Source comments disagree about whether the business-key unique constraint exists; actual DDL must resolve that. Grid saves do not compare the originally loaded values to current values, so stale edits can overwrite another operator's changes. Add an explicit identity/uniqueness contract, optimistic version checks and integration tests with concurrent transactions.

High — Packaged configuration is recoverable

DataRework.spec bundles .env into both executables; the spec itself notes this is obfuscation, not encryption. db/connection.py also has fallback database credentials. Require deployment configuration and use appropriate external secret storage and least-privilege database roles. UI admin checks alone are not database authorization.

Medium — Query work can block the desktop

Main-window database calls run synchronously. Identifier lists are unbounded, container aggregation reads every matching path, and record results are capped without ordered paging. Use worker threads, bounded suggestions and measured indexes after adding query timing instrumentation.

Medium — Serial activation can silently miss a record

_set_serial_active() updates by serial and does not check affected-row counts. A nonexistent replacement serial can leave usage accounting incorrect even if the rename succeeds. Validate inventory existence and expected cardinality before the transaction commits; add a missing-serial rollback case.

Medium — Some reload paths can discard pending edits

Container record opening and renaming guard pending changes, but ordinary record search reloads the table without an equivalent guard. Centralize dirty-state handling for searching, clearing, closing and future page changes. Preserve the existing two-stage parent/child rename semantics in the UI.

Proposed milestones
MilestoneConcrete deliverableExit criteria

Refactoring direction

Keep db/__init__.py as the compatibility facade. Extract reusable filter definitions from MainWindow into a typed query model, and move save/rename orchestration into an application service. Qt widgets should collect input and render results; the service should enforce edit rules independently of the UI. Introduce versioned schema migrations before extending persistence behavior.

Tradeoffs

A single new filter is a small change and does not require rewriting the application. A read-only joined view can enrich queries quickly but needs a separate write contract. A validated import pipeline is more work than manually inserting flat rows, but can maintain the relationships the existing save logic depends on. Raising the row limit is useful for a small controlled dataset; stable paging is the stronger long-term approach.

09Verification and operation

Run the isolated tests

# From the repository root, with project dependencies installed:
$env:QT_QPA_PLATFORM = "offscreen"
.venv\Scripts\python.exe -m unittest discover -s tests -p 'test_*.py' -v

The test_*.py suite covers database routing and transaction behavior, bulk deletes, identifier choices, container cards, scanner interaction, translations and images. test_user_tag.py covers rejected login, the three-value login signal and keyword tag forwarding on Save; the database transaction test checks the activation SQL parameters. The isolated suite passed all 48 tests after the tag integration fixes. The simulated offline diagnostic comes from the identifier-lookup failure test. The _test_*.py files are separate scripts; inspect them before running because they are not part of this discovery pattern and may exercise live database operations.

Know the deployment boundary

main.py is Windows-specific and schedules service setup during launch. UI development with DEV_MODE still uses the configured database and can still trigger service startup; it is not an isolated mock mode. Use test credentials and a dedicated test database for functional work.

build.ps1 builds the two executables using DataRework.spec and manages the existing service around the build. NSSM service setup directs stdout/stderr to logs/serial_store_sync.log. Service setup exceptions are logged rather than surfaced as a hard GUI startup failure.

Proposed operational signals: last successful sync time, cycle duration, failed cycles, records affected by writes, rejected conflicts and query duration. Set thresholds after measuring real volumes. A “saved” message confirms the grid transaction; it does not confirm a successful usage-count sync.
