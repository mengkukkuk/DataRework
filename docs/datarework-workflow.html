01Executive summary

DataRework is a PySide6 desktop tool for finding and correcting production packaging records in PostgreSQL. Operators sign in, then search a flattened record set, browse a carton → inner → display → unit tree, or report a damaged serial. Admin actions update records and packaging links together; a separate Windows service later recomputes used and damaged serial totals. Section 2 explains, end to end, what happens when DataRework.exe runs.

The database package already separates query, hierarchy, rename and synchronization concerns. The next useful step is to make that foundation safer (restrict editable columns, unify table configuration, add concurrency checks), then add explicit query fields and predictable paging. Password verification is implemented again (bcrypt); see the findings for the one remaining login bug.

500 rowsCurrent record query limit; no database ordering
One commitGrid records, edge updates and activation changes
10 secondsSync sleep after each cycle, not a freshness guarantee

To query more data: adding records, adding columns, joining reference data and returning more than 500 results are different changes. Section 7 explains each path. A new column can appear automatically in the grid, but a new filter still needs UI wiring.

Evidence: main_window.py, db/queries.py, db/edge_mirror.py, serial_store_aio.py.

Implemented

Startup sequence

  1. Load configuration

    main.py calls env_config.load_env() before importing db or main_window, because those modules read os.environ at import time. Precedence, highest first: real OS environment variables, the external .env next to the exe, then the .env embedded in the exe. The embedded file supplies every key, so a partial external file works. If DB_PASSWORD starts with enc: it is decrypted with the bundled key (envcrypt.py); a bad token raises an error that names the variable but never shows the value.

  2. Create the Qt application

    Sets the Windows AppUserModelID (so the taskbar uses our icon), the shared Latin+Thai font (typography.ui_font()) and the window icon.

  3. Show login, or skip it

    App opens LoginWindow. With DEV_MODE=true it skips login and opens the main window as admin (tag ADMIN); this still uses the real database and still starts the service.

  4. Register the sync service

    After the window is up, QTimer.singleShot(0, service_manager.ensure_service_running) installs and starts the service if needed. Installing needs administrator rights, so the exe relaunches itself elevated with --install-service (one UAC prompt) and exits without opening a GUI. Failures are logged and never block the GUI.

Login and roles

db.authenticate() reads public.app_users (password_hash, role, is_active, rework) and verifies the password with bcrypt.checkpw. It returns (role, role) on success, "not_active", "no_rework" or None; LoginWindow turns each into a message. The role value is used twice: as the permission and as the operator tag written to staging_serial_data.activate_by. admin and super admin (spelling variants normalised) can edit, rename and delete; other roles can search, browse and report damage only. A database outage at login shows "Unable to reach the database".

The main window

TabWhat the operator doesBacked by
RecordsFilter by month/day/year, assignment, product and an identifier (level + serial/roll/id). See and edit up to 500 flattened rows; mark rows for delete; Save commits everything once.query_rows, save_grid_changes
Container managerBrowse carton → inner → display cards with level marks and product images; open a container's records, rename it or delete it with everything inside.container_groups, rename_container, delete_container

Every database call goes through a small connection pool (db/connection.py: lazy, 1–3 connections, connect timeout and TCP keepalives) so a remote database does not pay a handshake per call. Search and container refresh run on a worker thread (db_worker.run_async) and tag their results with a generation counter so a slow, superseded response is dropped. Rename, delete and save remain synchronous and confirmation-gated. Errors appear in the status line; the footer Log button opens the in-memory log (last 500 entries, never written to disk) for the full text. Theme and language choices persist in QSettings("DataRework", "ProductionRework").

Background sync

SerialStoreSync.exe wakes every 10 seconds, counts activate and is_damaged serials per roll_no in staging_serial_data and writes serial_store.used_serials and damaged_serials. It is independent of the GUI: a "saved" message does not mean the totals have caught up. It logs errors only; a successful cycle writes nothing.

Changing the database without rebuilding

  1. Create .env next to DataRework.exe (copy .env.example) and list only the keys to change, for example DB_HOST.
  2. To avoid a plaintext password, run python encrypt_password.py on a developer machine, type the password, and paste the printed DB_PASSWORD=enc:... line. The key is bundled in the exes, so one value works on every machine built from the same secret.key.
  3. Relaunch the GUI. Restart the service so it re-reads the file: Restart-Service DataReworkSerialStoreSync from an elevated prompt.

The embedded .env and secret.key are obfuscation, not protection: anyone who can read the exe can unpack them. Restrict folder permissions and use a least-privilege database role.

Building and deploying

Run powershell -ExecutionPolicy Bypass -File build.ps1 from an elevated prompt. It stops the running service (PyInstaller cannot overwrite a locked SerialStoreSync.exe), creates secret.key on the first build (keep that file: a new key invalidates existing enc: values), runs PyInstaller with DataRework.spec, copies nssm.exe and .env.example into dist\, and restarts the service. Never run pyinstaller directly. Deploy by copying the whole dist\ folder; never commit or publish the exes.

04How functions work together

Choose an operation to follow its call path. The steps describe current code, including transaction boundaries.

Search records and browse containers

  1. Start the app and resolve access

    main() loads Qt → App opens LoginWindow → _attempt_login() calls db.authenticate() → MainWindow(username, permission, tag_name). The operator tag is required when constructing the window, including in tests. Authentication returns None (bad credentials), "not_active", "no_rework" or a (permission, tag) pair; each non-pair result becomes a login message. DEV_MODE skips login and grants the UI admin status. MainWindow.is_admin comes from db.is_admin_role(permission), which accepts the admin and super admin roles (case, space, underscore and hyphen variants normalised); both have identical rights.

  2. Discover columns and build filter choices

    _refresh_dependent_combos() calls get_columns() and fetch_distinct_values(). Cascade order is assignment → product, scoped by month/year. _refresh_tag_values() loads identifiers for the selected category and tag.

  3. Search using parameterized conditions

    _on_search() combines _current_conditions() and _category_tag_condition(), looks up primary keys, then dispatches _fetch_search_results() to db_worker.run_async, which looks up primary keys and calls query_rows() off the UI thread. The result (pk_columns, column_names, rows) is applied on the UI thread only if its generation is still current. Search and Save are disabled while loading. On the Container tab with pending grid edits, Search refreshes the cards instead of reloading the grid.

  4. Populate the record grid

    _populate_table() stores original values and primary keys for later comparison. Admins can edit if a primary key exists; container serial and roll columns remain read-only.

  5. Browse the same data as packaging

    _refresh_containers() (also on worker thread, same generation guard) → container_groups() → ContainerPanel.set_groups() → build_hierarchy(). Opening records passes the entire selected ancestor path to _on_search(container_path=...), preserving context for repeated serial names.

Edit and delete records

  1. Stage changes locally

    _on_item_changed() highlights edits; _delete_selected_rows() marks delete checkboxes. Neither writes to PostgreSQL. Each cell edit or Del tick is also recorded for the footer Undo/Redo buttons (blue arrow icons from the Windows Segoe icon font; Ctrl+Z, Ctrl+Y / Ctrl+Shift+Z): history entries are keyed by row primary key, so sorting does not break them; marking several rows is one step; a new edit drops the redo stack; and every reload (_populate_table(), _reset_table()) clears the history. The buttons show on the Records tab only, and undo only moves the unsaved state — Save is still what writes.

  2. Collect the intended operation

    _on_save() checks admin permission and primary keys, then _collect_changes() returns update pairs and delete key tuples. Empty strings become None. The operator confirms the change. If the save is refused whole (SharedEdgeError, SerialConflictError or SerialInventoryError, including SerialUnavailableError for a damaged or in-use serial), the transaction has rolled back, so _revert_pending_edits() puts every cell and Del tick back to the loaded value and the status line and Log carry the reason plus a reverted notice. The revert is itself one undo step, so Undo brings the edits back to fix the offending one. A connection failure or other exception keeps the edits in place for a retry.

  3. Read originals and validate shared edges

    save_grid_changes() opens one connection. _update_staging_serial_data() reads pre-edit rows, then drops every update or delete aimed at a row whose is_transfer flag is true (transfer.split_transferred()): a transferred row is frozen, the rest of the save carries on, and the skipped keys are returned. It then rejects serial/roll edits whose child edge is shared, raising SharedEdgeError. The flag is read from the same SELECT *, so there is no extra query; a table without an is_transfer column simply has nothing locked.

  4. Update packaging and serial state

    _apply_edge_change() updates affected edge endpoints. Unit serial changes deactivate the old serial and activate the new one. Grid saves pass tag_name=self.tag_name by keyword so the database schema remains public; activation updates write that tag to staging_serial_data.activate_by, via COALESCE so a call without a tag (a container rename) leaves the existing operator in place rather than nulling it. Deleting grid rows goes through remove_row_links() in db/deletion.py: the batch's unit serials are deactivated in one statement and each row's unit edge is removed. A display or inner edge is removed too, but only when the whole batch leaves nothing inside that container (no other row, and no other edge naming it as parent), judged bottom-up so emptying a display can empty its inner. A sibling unit is never affected.

  5. Write the grid changes and commit once

    queries._save_changes() updates/deletes the flattened records on the same cursor. Errors roll back both phases; unique violations become SerialConflictError. save_grid_changes() returns the skipped keys; _on_save() reports them ("N row(s) skipped: already transferred", or "Nothing was saved" when every row was skipped) and passes that text to the reload so it is not overwritten by "N row(s) loaded". On success, _on_search() reloads the grid. Roll usage totals update later.

Rename an entire packaging object

  1. Start with a dedicated dialog

    _rename_container() accepts a grid context action, footer action or container-card signal. It rejects pending grid edits and requires admin access.

  2. Preview the full impact

    container_rename_preview() counts matching flattened rows and edges, and raises TransferLockedError if any of those rows has is_transfer true. The user confirms the rename. This scope is serial + level, not the current grid filters or visible 500 rows.

  3. Rename every matching reference

    rename_container() checks the replacement serial with _serial_in_use(), refuses with TransferLockedError if any row of the container is transferred (a rename cannot skip rows: the edges and serial inventory change for the whole container), then _apply_serial_rename() changes child and parent edge mentions plus the flattened level column. Unit renames also update activation flags. This operation commits once.

  4. Optionally relabel children in a separate transaction

    After the parent commit, _relabel_children() loads container_children(). ChildRelabelDialog proposes child names; rename_children() validates (including the same transferred-row refusal for each child) and commits the selected batch atomically. Declining or failing this second stage leaves the parent rename in place.

  5. Refresh the view

    _on_search() reloads records; a rename from the manager also refreshes container groups.

Delete a container and everything inside it

  1. Choose the container

    _delete_container() is reached from the footer button, a right-click on a container serial cell, or the Delete link on a container card. It needs admin access and refuses while the grid has pending edits, because the reload would drop them. DeleteContainerDialog offers carton, inner and display (units are deleted from the grid) and never pre-selects a container; Enter, including a scanner's, only refreshes the listing.

  2. Review what is inside

    container_delete_preview() reads the container's own link, every link below it (a recursive query on staging_product_logs, so children with no saved row are found) and its rows in the configured flattened table. The dialog lists the contents indented by level with totals and names any parent that would be left empty. A serial linked under two parents, or with rows spread over two, is refused, as is a serial that names nothing, and so is a container with any row whose is_transfer is true (TransferLockedError, a ContainerDeleteError; a partial delete would leave links and serials disagreeing with the rows). The refusal is raised from the planning step, so the preview and the delete both enforce it.

  3. Confirm

    A final Yes/No box, defaulting to No, states the row, link and unit-serial counts and any parents that go with it.

  4. Delete in one transaction

    delete_container(..., table=STAGING_TABLE, tag_name, expected=preview) plans again inside the transaction and refuses if the counts differ from what was reviewed. It then releases the units' serials (one statement, recording the operator tag), deletes the links and the rows, and rolls back if the database reports a different count than planned. A parent left with nothing inside loses its own link too, by the same rule as a grid delete.

  5. Refresh the view

    The grid, and on the Container tab the cards, reload; the status line keeps the outcome and a note goes to the in-memory Log. Concurrent inserts into the container between the plan and the delete are narrowed by the recount, not excluded.

Recompute serial usage in the background

  1. Ensure the Windows service is running

    main() schedules ensure_service_running() using QTimer.singleShot(0, ...). NSSM supervises the source script or packaged SerialStoreSync.exe (AppDirectory is the exe folder, so the external .env is found). Installation may request Windows elevation.

  2. Fetch counts

    run_forever() calls sync_serial_counts_once(). asyncio.to_thread() runs _fetch_counts(): one query grouping staging_serial_data by non-null roll_no, counting activate (used) and is_damaged (damaged) together.

  3. Apply counts using another connection

    _apply_counts() writes serial_store.used_serials and damaged_serials in one UPDATE ... FROM (VALUES ...). Store rows whose roll is absent from the counts are reset to zero on both columns; an empty count map resets every store row. A null store roll number is not matched by NOT IN in a nonempty cycle.

  4. Log failures only, then repeat

    A failed cycle is logged with its traceback (logging.basicConfig(level=logging.ERROR), so successful cycles write nothing to logs/serial_store_sync.log) and the loop continues after the configured sleep, default 10 seconds. During a database outage that is one traceback per cycle. Read and write use separate connections, so counts can already be stale when written; the next successful cycle reconciles them.

Function sources: main_window.py, db_worker.py, edge_mirror.py, containers.py, serial_store_aio.py.

07Add more queryable data

Proposed development

Choose the kind of extension first. These are development recipes, not changes already applied to the application or database.

Example implementation path for batch_no

Assume operators need to find all units in a production batch. Define whether the batch belongs to an assignment, a unit or another entity before choosing where to store it. The example below assumes an ordinary column on the editable grid table.

  1. Inspect the deployed schema. Confirm that filling_product_logs is an appropriate writable base table, find its real primary key, and identify the upstream producer. If it is maintained by external transforms or triggers, change that pipeline too.
  2. Add a versioned migration and backfill. Add a nullable text field first. Populate it from an authoritative source and verify unmatched records before deciding on a required constraint. Existing data must remain searchable while the backfill runs.
  3. Let schema discovery expose the field. get_columns() and _populate_table() already load new columns. This does not create a filter and, for admins with a primary key, it may make the new field editable automatically. Explicitly protect derived or controlled fields.
  4. Register the filter and its widget. Update FILTER_COLUMNS, CASCADE_FIELDS, _build_filter_bar() and _cascade_combos. Insert the field at the appropriate cascade position.
  5. Add display labels. Add batch_no and the placeholder text to both locales/en.json and locales/th.json. Preserve raw column names and data values.
  6. Verify both views. Existing shared condition builders should feed record search and container aggregation. Test that batch selection refreshes identifier choices, clears correctly and scopes container counts consistently.

Add production records through a validated import

The current GUI supports search, updates, deletions and renames; it has no create-row or CSV import workflow. Adding arbitrary rows only to the flattened table can leave packaging and usage data inconsistent.

  1. Obtain the actual DDL, foreign keys, unique rules and upstream ingestion contract. Decide which source owns flattened-record generation.
  2. Build a separate import service/function with a dry-run result: accepted rows, rejected rows and reasons. Validate serials, label levels, roll existence, parent references and identifier uniqueness.
  3. Use a source-system record key for idempotency so retrying the same import does not duplicate units. Do not substitute serial text for a verified stable key.
  4. Write the required edge, serial-inventory, roll-inventory and flattened records through the authoritative pipeline in one appropriate transaction. If triggers derive one representation, do not also duplicate their writes.
  5. Reconcile unit counts, packaging paths and activation counts on a test database. Include invalid-parent, duplicate-record, missing-roll and rollback cases.
  6. Search using the imported record dates and assignment/product values; clear default month/year filters if necessary. Verify serial totals after a successful sync cycle.

Suggested new module: db/imports.py for validated persistence, with a separate UI preview. Keep import rules out of _populate_table(). Test fixtures should model real relationships, not just a flat list of rows.

Add related product or supplier data

Use a stable key such as a product ID rather than joining on a display name. A one-to-many join can duplicate unit records and inflate container counts; define whether a relationship is one-to-one, many-to-one or aggregated before exposing it.

  1. Introduce a versioned product/reference schema and a verified join key, with duplicate and orphan checks.
  2. Create an explicit read query or read-only database view projecting the extra fields. Keep the editable base-record ID separate from display fields.
  3. Mark joined/derived columns read-only and route edits to their owning entity. Do not send the projected row blindly to save_grid_changes().
  4. Extend filter metadata with allowed operators and typed values. Reuse the same join/filter semantics in record and container-count queries.
  5. Test missing reference data, duplicate matches and unchanged unit counts. Confirm that no joined column becomes implicitly writable.

Configuration caveat: pointing STAGING_TABLE at a view is not enough for an editable screen. Primary-key discovery may return no key, edge mirroring assumes the existing shape, and the current main-window rename calls still use default table arguments.

Query beyond the current 500-row cap

Increasing the limit alone does not provide predictable browsing. First define a stable ordering, then add paging and pass sorting into SQL.

  1. Choose an ordering backed by verified keys, for example created_at, id if those columns exist and id is unique. Decide how null dates sort.
  2. Add a page result contract with rows, continuation cursor and a has_more indicator. Fetch one extra row to detect the next page.
  3. Use keyset paging for large datasets, with bound cursor values and allowlisted sort identifiers. Ensure the next-page predicate matches the order exactly.
  4. Move search/aggregation to a Qt worker thread; deliver results to the GUI thread and ignore stale responses after filter changes.
  5. Block or resolve pending edits before changing pages. Preserve identities separately from display positions. Export all matches through an explicit export query rather than the currently loaded grid.
-- Proposed shape only; assumes non-null created_at and a unique id.
SELECT id, created_at, assignment_no, product_name
FROM public.filling_product_logs
WHERE assignment_no = %s
  AND (created_at, id) > (%s, %s)
ORDER BY created_at, id
LIMIT %s;
-- First page omits the cursor predicate; request page_size + 1 rows.

Acceptance check: load more than 500 matching test rows with duplicate timestamps. Traverse pages without duplicates or omissions in a fixed dataset, test both sort directions, and define expected behavior under concurrent inserts.

08Key findings and implications

These findings come from the inspected code. Severity expresses development priority; it is not a claim that a production incident has occurred.

High — Login crashes for an unknown username

Resolved: password verification is implemented again (bcrypt.checkpw), with is_active and rework gates. Still open: db/auth.py:authenticate() unpacks row before testing row is None, so an unknown username raises TypeError in the login slot instead of showing "Invalid username or password". Move the None check above the unpacking and add a test. Ensure production cannot enable the DEV_MODE admin bypass.

High — New columns and identity fields are editable by default

_populate_table() protects only the listed container serial/roll columns. Other columns, including keys and source/target IDs, may be editable for admins. _collect_changes() sends changed text with no column-type validation. Replace this with an explicit editable-field allowlist and typed validation at both UI and persistence boundaries.

High — Rename scope and table configuration need a single contract

Container renames match serial plus label level across the table, not the selected assignment or ancestor path. Verify whether serials are globally unique. Also, main-window preview/rename/child-relabel calls omit table=STAGING_TABLE, whereas grid search and save use it. With a nondefault configured source, these operations can refer to different flattened tables. Centralize dataset configuration and test a nondefault table.

High — Concurrency and database constraints are not established

Rename conflict checks occur before writes, without a visible locking strategy. Source comments disagree about whether the business-key unique constraint exists; actual DDL must resolve that. Grid saves do not compare the originally loaded values to current values, so stale edits can overwrite another operator's changes. Add an explicit identity/uniqueness contract, optimistic version checks and integration tests with concurrent transactions.

High — Packaged configuration is recoverable

Partly mitigated: an external .env next to the exe now overrides the embedded one, and DB_PASSWORD can be an enc: Fernet value (see the deployment boundary). The key (secret.key) is still bundled, so this is obfuscation. DataRework.spec bundles .env into both executables; the spec itself notes this is obfuscation, not encryption. db/connection.py also has fallback database credentials (a default host, user and password used when no .env value is set). Require deployment configuration and use appropriate external secret storage and least-privilege database roles. UI admin checks alone are not database authorization.

Medium — The is_transfer lock is app-side and has gaps

Implemented: grid saves skip transferred rows; container delete and rename refuse. Not covered: the standalone queries.save_changes() and update_staging_serial_data() (unused by the GUI) apply no lock; the check reads the row before the write, so a row flagged between the read and the write can still be changed (the statements do not repeat the condition); and a table without an is_transfer column silently locks nothing, so a mistyped or missing column disables the guard instead of failing. As with serial uniqueness, the durable fix is in the database (a trigger or WHERE is_transfer IS NOT TRUE on the writes). As of this change the live rpadata database has no is_transfer column; it must be added for the lock to take effect.

Medium — Query work can block the desktop

Resolved in part: search and container refresh now run on a worker thread (db_worker) over a pooled connection. Still synchronous: filter-combo suggestions (debounced), rename, delete, save and damage reporting. Identifier lists are unbounded, container aggregation reads every matching path, and record results are capped without ordered paging. Use worker threads, bounded suggestions and measured indexes after adding query timing instrumentation.

Medium — Some reload paths can discard pending edits

Container record opening and renaming guard pending changes, but ordinary record search reloads the table without an equivalent guard. Centralize dirty-state handling for searching, clearing, closing and future page changes. Preserve the existing two-stage parent/child rename semantics in the UI.

Low — Serial activation relies on a trimmed match, not the index

Resolved in part: _set_serial_active() now asserts cardinality. Activation callers pass required=True, so an affected-row count other than 1 raises SerialInventoryError and rolls the enclosing transaction back instead of leaving usage accounting short. Deactivation stays unchecked, since a serial already absent is already uncounted.

What remains is the data itself. staging_serial_data.serial_no stores a trailing space that filling_product_logs and staging_product_logs do not, and varchar comparison is not blank-padded, so every lookup was matching zero rows until the predicate became btrim(serial_no) = btrim(%s). That predicate is not sargable against the (serial_no, label_level_code) index. Normalize the stored values, then drop the btrim() on the column side; verify first that trimming introduces no duplicate serials.

Refactoring direction

Keep db/__init__.py as the compatibility facade. Extract reusable filter definitions from MainWindow into a typed query model, and move save/rename orchestration into an application service. Qt widgets should collect input and render results; the service should enforce edit rules independently of the UI. Introduce versioned schema migrations before extending persistence behavior.

Tradeoffs

A single new filter is a small change and does not require rewriting the application. A read-only joined view can enrich queries quickly but needs a separate write contract. A validated import pipeline is more work than manually inserting flat rows, but can maintain the relationships the existing save logic depends on. Raising the row limit is useful for a small controlled dataset; stable paging is the stronger long-term approach.

Know the deployment boundary

main.py is Windows-specific and schedules service setup during launch. UI development with DEV_MODE still uses the configured database and can still trigger service startup; it is not an isolated mock mode. Use test credentials and a dedicated test database for functional work.

build.ps1 builds the two executables using DataRework.spec and manages the existing service around the build. It also copies nssm.exe (repo root first, else PATH) into dist\; service_manager._nssm_path() uses the nssm.exe next to the exes (repo root when run from source) and falls back to PATH, so a copied dist\ folder registers the service without a system-wide NSSM install. NSSM service setup directs stdout/stderr to logs/serial_store_sync.log; the sync logs at ERROR level only, so the file stays small and any content means a failed cycle. Service setup exceptions are logged rather than surfaced as a hard GUI startup failure.

Configuration loading (implemented): both entry points call env_config.load_env() before importing db. Precedence is real OS environment, then an external .env in the exe folder, then the .env embedded by DataRework.spec; a partial external file only needs the keys being changed. Edits apply on the next GUI launch or after Restart-Service DataReworkSerialStoreSync; no rebuild. python encrypt_password.py prompts for the password and prints DB_PASSWORD=enc:... (Fernet via envcrypt.py, key in the gitignored secret.key, which build.ps1 creates once and which must stay stable across builds). bcrypt is not usable here because it is a one-way hash. build.ps1 never touches dist\.env and copies .env.example to dist\.env.example.

Proposed operational signals: last successful sync time, cycle duration, failed cycles, records affected by writes, rejected conflicts and query duration. Set thresholds after measuring real volumes. A “saved” message confirms the grid transaction; it does not confirm a successful usage-count sync.
